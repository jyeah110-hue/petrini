## 주요 트러블슈팅

### 1. XSS 필터 - 라이브러리 호환성 문제
**문제**: 보안 라이브러리 `lucy-xss-filter`가 Jakarta EE와 호환되지 않음
**해결**: 서블릿 의존성이 없는 `lucy-xss`로 전환하고, Wrapper 클래스를 직접 구현하여 필터 내부에서 lucy-xss를 호출하는 방식으로 재구성
**한계 및 인지사항**: `@RequestParam`은 필터로 처리되지만 `@RequestBody`는 별도 처리 로직이 필요하며, Spring Security를 적용하면 이러한 처리가 자동화된다는 점을 학습

### 2. CSRF 토큰 검증 직접 구현
**구현**: 토큰 생성 Util과, 모든 POST 요청을 가로채 토큰을 검증하는 Interceptor를 직접 구현
**배경 학습**: 로그인된 브라우저를 이용해 악의적 사이트에서 몰래 요청을 보내는 CSRF 공격 원리를 이해하고 방어 로직을 설계했으며, Spring Security 사용 시 필터 수준에서 자동 처리된다는 점과 비교하며 이해도를 높임

### 3. 보안 응답 헤더 설정
클릭재킹 방지, 뒤로가기 시 인증 페이지 캐시 노출 방지, 외부 사이트 이동 시 Referrer 정보 최소화(도메인만 전달) 등 보안 헤더를 설정

### 4. AOP 로깅 설계
**문제**: 기존 로그가 레벨(DEBUG/INFO/WARN/ERROR) 구분 없이 콘솔에만 출력되어 운영 환경에서 추적이 어렵고, 동기 I/O 방식이라 성능 저하 우려가 있었음
**해결**: AOP로 컨트롤러 진입점에 로깅을 적용해 콘솔과 파일에 동시 기록
**설계 근거**: 서비스 레이어까지 로깅할 경우 하나의 요청에 컨트롤러 로그와 서비스 로그가 중복 발생함 → 컨트롤러 단일 지점 로깅만으로 요청 처리 시간 추적에 충분하다고 판단했으며, 필요 시 Pointcut 추가만으로 서비스 레벨 로깅까지 확장 가능하도록 설계

### 5. 배포 환경 디버깅의 어려움
**문제**: 배포 환경에서는 디버깅 모드 사용이 불가능해 오류 원인 파악이 어려웠고, 특히 보안 기능 적용 이후 발생한 CSRF 토큰 충돌, DB 연결 장애의 원인을 찾는 데 시간이 소요됨
**해결**: 로그 기록을 기반으로 원인을 단계적으로 역추적하며 해결

## 소감

AI가 생성한 결과물을 그대로 내 것이라 여기지 않고, 
핵심 원리를 이해해 직접 개선·수정할 수 있는 능력을 기르는 것이 중요하다는 것을 느꼈습니다. 
이번 프로젝트에서 처음으로 보안을 공부하며 예상대로 어려움을 겪었지만, 
XSS·CSRF의 동작 원리를 하나씩 파악해가는 과정이 흥미로웠습니다. 
앞으로 보안의 특성을 차근차근 익히고 더 많은 코드를 보며, 
실무에서는 이런 기능들을 어떻게 구현하는지 깊이 알아가고 싶습니다. 
또한 오류를 잘 기록해두어 동일한 문제 발생 시 빠르게 대응할 수 있도록 하는 습관의 중요성도 느꼈습니다.
